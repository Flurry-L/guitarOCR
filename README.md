# GuitarOCR

将乐谱 PDF 或图片识别为可编辑的乐谱，对照原图校对后导出 GP5、MusicXML 或项目备份。

![乐谱编辑器](docs/assets/score-editor-0.1.webp)

支持 TAB、五线谱、五线谱＋TAB，以及吉他、贝斯、鼓、钢琴等乐器的多轨谱面。可校对音符、节奏、奏法、和弦名和指法图。

当前技术路线与人工校对边界见下方[识别机制](#识别机制)。本地整理后的模型尚未发布到下方历史下载版本。

## 使用

[下载应用](https://github.com/Flurry-L/guitarOCR/releases/tag/v0.1.0) · [安装与设备要求](docs/usage.md) · [自托管部署](docs/server.md)

提供 Apple 芯片 Mac 和 Windows 客户端。Windows 自动选择设备，兼容的 NVIDIA 显卡按需获取加速组件。Linux、Intel Mac 和自托管服务从源码构建。

1. 打开应用，导入 PDF 或图片，点击「开始识别」。首次识别需下载模型，大小以应用显示为准。
2. 对照原谱修改音符，按「确认并继续」逐小节核对。
3. 导出 GP5 或 MusicXML；需要保留原图和校对进度时，下载项目 ZIP。

「项目」中可搜索乐谱、查看识别进度、停止或继续处理。内置示例可直接练习编辑，无需下载模型。详细操作见[使用说明](docs/usage.md)。

## 识别机制

产品输入是 PDF 渲染出的页面或用户图片。PDF 字体、矢量线条和源工程只用于生产与核验训练真值，不作为产品推理的补救通道。

### 识别流程

1. **版面检测**：PP-DocLayout 检测三种小节区域和谱头、谱号、速度、标注。输入等比缩放并补白，保留原图坐标。有限的多尺度视图补充候选；质量网络结合图像和视图间的一致性，对已有框筛选、排序、去重，不生成新框或猜小节数。
2. **结构与身份**：学习谱行分组、声部关系、可见乐器名、谱表类型、谱号和跨行延续。名称只用一个模型定位，完整谱行和名称裁图一起交给 OCR 读取；不能确认时保留未知，要求人工指定。不合法的声部分配直接报错，不按重复行数、乐器类别或上一行模板补出身份。位置接近不等于同一乐器。
3. **单图观察与组谱**：小节模型只接收当前小节图，输出可见弦品、谱位、节奏、印出的状态变化和连线端点；看不见的值保留未知。共用 Rust 核心按谱表顺序拼接延音、奏法和八度范围，继承有证据的拍号、调号与谱号，再生成 M 文本及产品音高。研究、桌面和服务使用同一组谱实现。标题、乐器和谱号等信息由独立的信息模型读取；两个模型按阶段切换，同一时刻只驻留一个。
4. **和弦**：小节框保留本节上方的和弦名称与指法图，左右仍以小节线为界。观察模型读取名称及其拍点，指法数字不生成演奏音符；跨出小节的完整网格由独立标注框保存，两个小模型读取指法几何，再关联到已有的本地和弦事件。谱首和弦库不生成演奏拍点或额外音轨；不确定的图、指法或归属保留待确认。
5. **可见奏法**：PM / let ring 和延续线随单图观察输出。只有相邻小节的端点、声部与已知类型相容且对应唯一时才连接；不以虚线像素样式或固定高度猜类型。只有延续线而没有标签时先保留未知，组谱后再确定。
6. **IR 与人工校对**：整谱保存在 ScoreIR，单小节序列化为 `M` 文本。训练、推理、编辑和保存只接受当前协议，不迁移旧文本或旧识别日志。缺少品位、音高或节奏的小节保存原始观察和待补全内容，不生成休止占位；补全后重新组谱。保存、重开、撤销与导出使用同一份音乐语义。用户修正框、声部、音符和标注；GP5 / MusicXML 是 IR 的导出结果。

### 能力边界

- 漏框、严重合框和完全未识别的谱行由用户补框或改框。质量网络只能选择它收到的候选。
- 图片中没有印出的播放参数、逐音力度、源文件隐藏开关不能可靠恢复，不作为正确标签。
- 没有文字标记、归属不明的延续线由用户核对范围。只有明确的八度标记进入音高前文。
- 陌生版式、模糊图像、复杂连线、跨系统身份和指法图细节仍可能识别错。语法正确不代表音符正确，导出前仍需对照原谱。
- 当前观察模型尚不能把鼓谱位置可靠映射为鼓件编号；保留未知，需人工补全。
- 小节观察尚未覆盖反复记号、段落与跳转指令的自动读取；框内保留了图像，不代表已经转换成播放语义。
- GP5 的弦数、声部数、编码及指法图库表示能力有限；完整工作应保存项目 ZIP。

每项任务只保留当前采用的推理路径。用户发起的小节重识别、人工待核对状态和文件保存校验各有明确用途；未采用的实验选项、历史模板补救及其专属测试不进入主线。增加第二模型或额外重试前，应先用相同输入做对照，确认收益。
